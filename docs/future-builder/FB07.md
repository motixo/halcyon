# FB07 — shared provider demand

Implemented locally on 2026-10-26 for the Clock/Weather foundation slice. [Exact evidence](evidence/fb07-20261026.json) records source, artifacts, checks and limits. Current singleton preferences and profile formats are unchanged.

## Implemented

- Weather demand is keyed by the full existing location binding: name and validated latitude/longitude. Signed zero is normalized. Open-Meteo, metric units, requested fields, automatic timezone and three forecast days are fixed request inputs; adding a query variant requires extending the key.
- Consumers of the same key share one request and an immutable `Arc` observation. Different bindings have separate observations and deadlines. The fastest active consumer sets cadence. Removing one consumer leaves the others subscribed.
- The owner permits four active or cancelling jobs and 32 retained keys, with at most 64 demand records. The existing application uses one location; multi-key consumers are exercised in fixtures without introducing duplicate-widget persistence or UI.
- Releasing the last consumer aborts the fetch. Its slot stays occupied until the worker acknowledges completion. Every delivery checks its exact request token and current demand, including the A → B → A case. A late response cannot clear a newer flight, change readings/errors, or write a cache.
- Typed snapshots carry binding, revision, observation time in the data, refreshing/failure flags, and loading, ready, stale, unavailable or disconnected state. Existing Clock/Weather presentation remains the rendering boundary.
- Weather fetches have a 15-second deadline and a 256 KiB encoded response limit, enforced for declared and streamed bodies. Failures retain useful readings with their age and retry after 120 seconds.
- Cache persistence runs only after accepted delivery. One writer drains one replaceable pending snapshot; slow disk I/O cannot accumulate workers or an unbounded queue. Writes run in order, with newer pending data replacing superseded values. A worker lease prevents an old completion from releasing a newer writer. Existing cache format and owner-only permissions remain intact; disk I/O never holds the producer lock or runs on the UI thread.
- The standalone Weather widget and Daily overview hand demand over without restarting the request. Hiding widgets or their assigned display releases demand. Startup retains its existing prefetch until the first output observation. Local previews accept no live demand.
- Clock and Daily overview read one captured wall-clock observation, advanced through the existing shared wake. Hidden/disconnected Clock consumers do not advance it. No per-view timer was added.

The existing live Weather fields are a bounded presentation projection of accepted observations, not an independent scheduler or persistent source of truth. Other providers retain their current owners. This task does not introduce a generic plugin/provider framework.

## Validation

123 distinct focused regressions pass, including 18 new cases. They cover:

- Same-key coalescing, shared observation identity and independent bindings.
- Reference removal, cadence changes, bounded concurrency/queue capacity and resume deadlines.
- A → B → A stale success/failure delivery and current-flight preservation.
- Started-worker cancellation, owner-drop cancellation and timeout/retry.
- Snapshot states, invalid source identity, cache worker ordering and file permissions. A blocked-writer fixture verifies bounded coalescing, unblocked producers and recovery after a task is dropped before starting.
- A real loopback HTTP server with the production parser, one request for two consumers, and declared/chunked oversized responses.
- Runtime location changes, standalone/overview handover, hidden/disconnected output demand, and the same captured Clock text in both native views.
- Existing runtime, layout, display, Weather stale-state, Clock geometry, preview-action and compact Settings behavior.

Cancellation tests wait for the exact worker to signal that it started before aborting it, then require acknowledgement within a 100 ms test timeout. They do not infer startup from a fixed sleep. All network fixtures use loopback; live weather requests were not used for acceptance.

The local release build, scoped formatting and whitespace checks pass. The five preexisting wizard-repair hashes remain unchanged. This stage changes provider ownership and delivery, so FB06's saved visual/performance records remain historical evidence; they were not relabelled as fresh FB07 measurements.
